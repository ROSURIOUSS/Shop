# GameZone — интернет-магазин игровых аксессуаров

**GameZone** — многостраничный интернет-магазин игровой периферии на Django.
Это учебный проект для контрольной работы по Python и Django: реальный серверный
функционал (ORM, сессии, формы, CRUD, админ-панель), а не статическая вёрстка.

> Проект носит демонстрационный характер: товары, цены и контакты вымышленные,
> платёжная система не подключена. Заказы сохраняются в базе данных SQLite.

---

## Что реализовано

- **Каталог** с серверным поиском (`?q=`), фильтром по категориям, диапазоном цены,
  сортировкой и пагинацией (12 товаров на страницу).
- **Категории** — список и отдельные страницы категорий (`/categories/<slug>/`).
- **Карточка товара** — изображение, характеристики (JSON), наличие, похожие товары.
- **Отзывы и рейтинги** — оценка от 1 до 5 и текст отзыва. Писать отзыв может
  только тот, кто уже заказывал этот товар, поэтому на сайте нет выдуманных
  оценок. Средняя оценка и звёзды видны в карточке и в каталоге, есть сортировка
  «По рейтингу». В админке отзывы можно скрывать и удалять.
- **Корзина на сессиях** — добавление, изменение количества, удаление, очистка;
  цены всегда пересчитываются на сервере по данным базы.
- **Промокоды** — скидка процентом или фиксированной суммой, с минимальной
  суммой заказа, сроком действия и лимитом применений. Код вводится в корзине,
  скидка пересчитывается только на сервере и сохраняется в заказе вместе
  с промокодом. Демо-коды: `GAMEZONE10` (−10 %) и `WELCOME200` (−200 ₴ от 2000 ₴).
- **Избранное** — сердечко в карточке товара, отдельная страница `/wishlist/`
  и счётчик в шапке. Список хранится в сессии, поэтому доступен и без входа.
- **Жизнь заказа в кабинете** — страница заказа с таймлайном
  «оформлен → подтверждён → отправлен → завершён», составом, скидкой и кнопкой
  отмены. При отмене товары возвращаются на склад, а промокод освобождается.
- **Печатный чек** — отдельная страница заказа с таблицей позиций и `@media print`:
  печатается из браузера или сохраняется в PDF, без сторонних библиотек.
- **Быстрые действия с заказами в админке** — кнопки «Подтвердить», «Отправить»,
  «Завершить», «Отменить» прямо в карточке заказа, плюс те же действия пачкой
  из списка. Показываются только допустимые переходы, отмена возвращает товары
  на склад и освобождает промокод.
- **Счётчик новых заказов** — в шапке админки видно «3 новых заказа» со ссылкой
  на отфильтрованный список; цифра обновляется на каждой странице.
- **«С этим покупают»** — блок в карточке товара, собранный по реальным заказам
  (какие товары чаще всего покупают вместе с этим). Без данных блок не выводится.
- **Восстановление пароля** — письмо со ссылкой на смену пароля, срок действия
  24 часа, ссылка одноразовая. Без настроенного SMTP письмо выводится в консоль
  сервера, поэтому ничего не «теряется» молча.
- **Оформление заказа** — валидация формы, проверка остатков, создание `Order` и
  `OrderItem` с фиксацией цены, списание остатков — всё в одной транзакции.
- **Аккаунты покупателей** — регистрация, вход, выход, личный кабинет с историей
  заказов и данными для доставки. Оформление заказа доступно после входа, каждый
  заказ привязан к покупателю.
- **Журнал активности** — отдельный раздел админки «Активность и IP-адреса»:
  посещения (IP, страница, браузер, система, код ответа) и события покупателей
  (регистрация, входы, неудачные попытки, заказы). IP сохраняется и в самом заказе.
- **Сводка в админ-панели** — на главной странице `/admin/` видны выручка за
  сегодня, 7 и 30 дней и за всё время, статусы заказов, топ товаров, остатки,
  посещаемость и последние заказы. Все цифры считаются агрегатами ORM по
  реальным данным, графики нарисованы на чистом CSS.
- **Резервные копии данных** — команды `backup_data` и `restore_data`, а также
  `backup.bat` / `restore.bat`: пользователи, профили, заказы и товары
  сохраняются в один JSON-файл и возвращаются обратно.
- **Работа с внешней базой PostgreSQL** — достаточно задать переменную
  `DJANGO_DATABASE_URL`, код менять не нужно.
- **Страница успеха** доступна только из сессии, в которой оформлен заказ.
- **Контакты** с формой обратной связи (сообщения сохраняются в БД).
- **Выгрузка в CSV** — в списках админки есть действие «Выгрузить в CSV»:
  товары, заказы (и отдельно позиции заказов), отзывы, профили, обращения и
  оба журнала активности. Файл открывается в Excel с русскими буквами и
  учитывает текущие фильтры списка.
- **Метка низкого остатка в админке** — в списке товаров цветная метка
  «Заканчивается» / «Нет в наличии» / «Снят с продажи» / «Достаточно»,
  фильтр по остатку и предупреждение в форме товара.
- **Django Admin** — управление категориями, товарами, заказами, отзывами,
  профилями покупателей и обращениями.
- **Оформление админ-панели** — тёмная тема в стиле витрины: та же палитра,
  шрифт Inter, логотип и фирменные акценты на всех страницах, включая экран
  входа. Свой CSS, без сторонних библиотек.
- **Адаптивный дизайн** (десктоп, планшет, смартфон), тёмная premium-тема.

## Технологии

- Python 3.12+, Django 6.1, SQLite
- HTML5, CSS3 (Grid/Flexbox), немного JavaScript (только UI)
- Django Templates, Django ORM, Forms, Sessions, Authentication (`django.contrib.auth`), CSRF-защита

## Запуск на Windows

### Быстрый способ (в один клик)

Дважды кликните **`run.bat`** — батник сам найдёт Python, подготовит окружение,
установит зависимости, применит миграции, добавит демо-товары (если база пуста),
предложит создать администратора и запустит сервер, открыв магазин в браузере.

| Файл | Что делает |
|---|---|
| `run.bat` | Полный запуск: окружение + зависимости + база + администратор (по желанию) + сервер + браузер |
| `run.bat 8080` | То же самое, но на другом порту — удобно, если 8000 занят |
| `create_admin.bat` | Отдельное создание администратора для входа в `/admin/` (логин и пароль вводятся видимым текстом) |
| `backup.bat` | Сохранить пользователей, заказы и товары в файл `backups\gamezone-<дата>.json` |
| `restore.bat` | Вернуть данные из самой свежей копии (или перетащить файл копии на батник) |

Что ещё делает `run.bat`, чтобы запуск был удобнее:

- **Повторный старт быстрый.** Зависимости устанавливаются один раз: если Django
  и Pillow уже стоят, а `requirements.txt` не менялся, `pip` не запускается.
- **Не создаёт второе окружение.** Если рядом с папкой проекта уже есть `.venv`
  (так бывает, когда проект открыт в PyCharm), батник использует его.
- **Не воюет за порт.** Если порт занят (сервер уже запущен из PyCharm или
  вторым окном), батник предложит открыть работающий магазин в браузере
  или выбрать другой порт.
- **Сам предлагает создать администратора**, если в базе его ещё нет.
  Отказаться можно просто нажав Enter — тогда позже запустите `create_admin.bat`.
- **Браузер открывается, когда сервер уже слушает порт**, поэтому страница
  не встречает ошибкой подключения.

Чтобы остановить сервер — нажмите `Ctrl+C` в окне батника или закройте его.

Совет: сделайте ярлык — правый клик по `run.bat` → «Отправить» →
«Рабочий стол (создать ярлык)». Тогда запуск магазина будет в один клик
прямо с рабочего стола.

### Запуск из PyCharm (зелёной стрелкой)

Это тот же `runserver`, только без батника — сервер работает на вашем ПК.

**PyCharm Professional:**

1. `Run` → `Edit Configurations…` → `+` → `Django Server`.
2. Interpreter — `.venv` вашего проекта.
3. Host `127.0.0.1`, Port `8000`, `OK` — и запускайте.

**PyCharm Community** (отдельной Django-конфигурации там нет,
подходит обычная конфигурация Python):

1. `Run` → `Edit Configurations…` → `+` → `Python`.
2. `Script path` — путь к `manage.py` в папке проекта.
3. `Parameters` — `runserver`.
4. `Working directory` — папка проекта (там, где лежит `manage.py`).
5. Interpreter — `.venv`, `OK` — и запускайте.

Магазин откроется на <http://127.0.0.1:8000/>. Не держите сервер из PyCharm
и `run.bat` одновременно: оба занимают порт 8000. Если порт уже занят,
`run.bat` сам предложит открыть работающий магазин или выбрать другой порт.

### Ручной запуск (пошагово)

1. Установите [Python 3.12+](https://www.python.org/downloads/) (отметьте галочку «Add to PATH»).
   Django 6.1 требует Python 3.12 или новее — на более старых версиях
   зависимости не установятся.

2. Откройте папку проекта в терминале (PowerShell или «Командная строка»):

   ```
   cd путь\к\папке\GameZone
   ```

3. Создайте виртуальное окружение:

   ```
   py -m venv .venv
   ```

   Если лаунчер `py` не работает, используйте `python -m venv .venv`.
   Если `python` выводит ошибку про `WindowsApps\python.exe` — это подставла
   Microsoft Store, а не настоящий Python: установите Python с python.org.

4. Активируйте окружение:

   ```
   .venv\Scripts\activate
   ```

5. Установите зависимости (Django и Pillow):

   ```
   pip install -r requirements.txt
   ```

6. Примените миграции:

   ```
   python manage.py migrate
   ```

   Если вы изменяли модели, сначала выполните `python manage.py makemigrations`.
   Если изменений нет, команда сообщит «No changes detected» — это нормально.

7. Заполните базу демонстрационными категориями и товарами:

   ```
   python manage.py seed_data
   ```

   Команду можно запускать повторно: данные не дублируются, ничего не удаляется.
   С ключом `--if-empty` заполнение выполнится только при пустой базе
   (так работает `run.bat`, чтобы не затирать ваши правки в админ-панели).

8. Создайте администратора (пароль придумайте сами, в коде пароля нет):

   ```
   python manage.py createsuperuser
   ```

   Обратите внимание: символы пароля при вводе в консоли не отображаются —
   это стандартное поведение, просто набирайте пароль и нажимайте Enter.
   Если консоль не принимает ввод пароля, используйте `create_admin.bat` —
   там логин и пароль вводятся обычным видимым текстом.

9. Запустите сервер разработки:

   ```
   python manage.py runserver
   ```

10. Откройте в браузере:
    - магазин: <http://127.0.0.1:8000/>
    - админ-панель: <http://127.0.0.1:8000/admin/>

## Основные маршруты

| Адрес | Страница |
|---|---|
| `/` | Главная |
| `/catalog/` | Каталог (поиск `?q=`, фильтры `?category=`, `?min_price=`, `?max_price=`, `?sort=`) |
| `/categories/` | Категории |
| `/categories/<slug>/` | Товары категории |
| `/product/<id>/` | Карточка товара с отзывами |
| `/product/<id>/review/` | Оставить или изменить отзыв (POST, только покупатель) |
| `/cart/` | Корзина, промокод и скидка |
| `/cart/coupon/` | Применить промокод (POST) |
| `/wishlist/` | Избранное |
| `/wishlist/toggle/<id>/` | Добавить или убрать товар (POST) |
| `/checkout/` | Оформление заказа (нужен вход) |
| `/order/success/` | Успешный заказ |
| `/order/<номер>/receipt/` | Печатный чек заказа |
| `/about/` | О магазине |
| `/contacts/` | Контакты |
| `/accounts/register/` | Регистрация покупателя |
| `/accounts/login/` | Вход |
| `/accounts/logout/` | Выход (только POST) |
| `/accounts/profile/` | Личный кабинет: данные и история заказов |
| `/accounts/profile/edit/` | Изменение имени, email и адреса доставки |
| `/accounts/password/` | Смена пароля |
| `/accounts/password-reset/` | Восстановление пароля по email |
| `/accounts/orders/<номер>/` | Заказ в кабинете: статус, состав, отмена |
| `/admin/activity/visitlog/` | Журнал посещений: IP, страницы, браузеры |
| `/admin/activity/authevent/` | События покупателей: входы, регистрации, заказы |
| `/admin/` | Админ-панель: сводка магазина и разделы данных |

Сейчас тестов 271, и все они проходят на Django 6.1. Покрыты:

- модели: цены, номер заказа, фиксация цены в позиции заказа;
- корзина: добавление, ограничение остатком, удаление, очистка;
- оформление заказа: создание `Order`/`OrderItem`, списание остатков,
  отказ при нехватке товара, обязательный вход, привязка заказа к покупателю;
- строка подключения к базе: очистка от пробелов, переносов строк, кавычек,
  `&amp;` и имени переменной, восстановление потерянной схемы, понятные
  ошибки на разметке и чужой схеме, отсутствие пароля в тексте ошибки;
- команда `db_status`: предупреждение про SQLite на хостинге, отчёт о внешней
  базе, сообщение об ошибке подключения при `--ping`;
- резервные копии: состав файла, создание папок, хранение пароля только хэшем,
  копирование журнала по флагу, восстановление удалённых пользователей,
  профилей и заказов вместе со связями, режим просмотра без изменения базы,
  ошибки на отсутствующем и постороннем файле;
- оформление админ-панели: своя тема подключена на главной, в списках
  товаров, заказов, журнала и пользователей, а также на экране входа; палитра
  админки совпадает с витриной; нужные CSS-переменные переопределены;
- статусы заказов: допустимые переходы для каждого статуса, смена статуса,
  отказ при неверном переходе и неизвестном коде, отмена с возвратом остатков
  и освобождением промокода, кнопки в карточке заказа, запрет перехода
  без права изменения, массовые действия и пропуск недопустимых заказов,
  счётчик новых заказов в шапке, его склонение и скрытие без прав;
- промокоды: процент и фиксированная сумма, округление, скидка не больше
  суммы, минимальная сумма заказа, сроки, лимит применений, нормализация кода,
  запрет повторов без учёта регистра и пробелов (в форме и в модели),
  допустимые символы, кириллические коды на витрине,
  применение и снятие в корзине, понятные сообщения, фиксация скидки в заказе,
  подсчёт применений и освобождение промокода при отмене;
- избранное: добавление и удаление, страница, счётчик в шапке, активное
  сердечко в каталоге, запрет GET-запроса, возврат на предыдущую страницу
  с защитой от открытого редиректа;
- жизнь заказа: страница заказа только для владельца, шаги таймлайна,
  отмена с возвратом остатков, запрет отмены после отправки, доступ к чеку
  для владельца, персонала и сессии после покупки;
- «с этим покупают»: пара товаров из одного заказа, игнор отменённых заказов,
  порядок по частоте, скрытие отсутствующих товаров, отсутствие блока без данных;
- восстановление пароля: письмо существующему адресу, отсутствие письма и
  подсказок для чужого адреса, проход по ссылке и смена пароля, одноразовость
  ссылки, экраны «письмо отправлено» и «пароль изменён»;
- шаблоны: парность тегов `{% %}` и `{{ }}` во всех файлах, отсутствие
  опечаток вида `%>`, публичные и закрытые страницы не выводят теги как текст;
- отзывы и рейтинги: отзыв только от покупателя товара, отказ без заказа и
  при отменённом заказе, повторная отправка обновляет свой отзыв и не трогает
  чужой, проверка оценки (1–5), обязательный вход, запрет GET, уникальность
  отзыва на товар, средняя оценка только по видимым отзывам, звёзды и рейтинг
  в карточке, каталоге и админке, скрытый отзыв не показывается, сортировка
  «По рейтингу», склонение «1 отзыв / 2 отзыва / 5 отзывов»;
- выгрузка в CSV: заголовки и данные, разделитель «;», BOM для Excel, имя файла
  с датой, учёт фильтров списка, выгрузка позиций заказов, журналов и отзывов,
  доступ пользователю с правом только на просмотр, закрытый доступ остальным;
- метка низкого остатка: «Заканчивается», «Нет в наличии», «Снят с продажи»,
  «Достаточно», фильтр по каждому состоянию, предупреждение в форме товара,
  общий порог со сводкой;
- сводка админ-панели: выручка и средний чек по периодам, исключение
  отменённых заказов, топ товаров по проданным штукам, товары с низким
  остатком, последние заказы и обращения, счётчики активности, скрытие
  разделов без прав на просмотр, доступ только для персонала;
- журнал активности: определение IP за прокси (`X-Forwarded-For`, `X-Real-IP`,
  IPv6, некорректные заголовки), распознавание браузера и системы, запись
  посещений и событий, пропуск статики, отключение журнала переменной
  окружения, обрезка длинных значений, доступ к разделу админки, очистка
  старых записей командой `clear_activity_log`;
- аккаунты: регистрация с созданием профиля и автоматическим входом, отказ
  при занятом email и слабом пароле, вход и выход, доступ к кабинету только
  для своих, подстановка данных профиля в форму заказа, изменение данных
  и смена пароля без выхода из аккаунта;
- команда `ensure_admin`: создание администратора, пропуск без переменных
  окружения, пропуск при существующем администраторе, защита от перезаписи
  обычного пользователя;
- боевой режим (`DEBUG=False`): POST с доверенного домена проходит,
  с чужого домена и без CSRF-токена отклоняется (403), чужой `Host` — 400.

## Аккаунты покупателей

Заказы привязаны к аккаунту, поэтому оформление (`/checkout/`) доступно только
после входа. Гости могут свободно смотреть каталог и собирать корзину: она
живёт в сессии и не теряется после входа.

| Действие | Адрес |
|---|---|
| Зарегистрироваться | `/accounts/register/` |
| Войти | `/accounts/login/` |
| Выйти | Кнопка выхода в шапке и в кабинете (POST, защищена CSRF) |
| История заказов и данные | `/accounts/profile/` |
| Изменить имя, email, телефон, город, адрес | `/accounts/profile/edit/` |
| Сменить пароль | `/accounts/password/` |

Как это работает:

- при регистрации создаётся пользователь и связанный с ним профиль `Profile`
  (телефон, город, адрес доставки);
- данные профиля автоматически подставляются в форму оформления заказа,
  а указанные в заказе контакты сохраняются обратно в профиль;
- в кабинете видны только собственные заказы — со статусом, составом и суммой;
- пароли хранятся в базе только в виде хэша, в открытом виде нигде не выводятся;
- удаление аккаунта не стирает историю: заказ остаётся в базе, а поле
  «покупатель» у него обнуляется;
- письма не отправляются — это учебный проект без почтового сервера.

## Журнал активности и IP-адреса

В админ-панели есть отдельный раздел **«Активность и IP-адреса»** — он не смешан
с товарами и заказами. Внутри два журнала.

**Журнал посещений** (`/admin/activity/visitlog/`) — каждое обращение к сайту:

| Поле | Что показывает |
|---|---|
| IP-адрес | адрес посетителя, кликабельный, есть поиск |
| Посетитель | аккаунт, если человек вошёл, иначе пусто (гость) |
| Страница | какой адрес открыт, например `/catalog/` или `/checkout/` |
| Метод и код ответа | `GET`/`POST` и результат (`200`, `404`, `302`, `403`) |
| Браузер и система | например `Chrome` и `Windows 10/11`, `Safari` и `iOS (iPhone)` |
| Откуда пришёл | страница-источник (Referer) |
| Время | дата и время обращения |

Есть фильтры по методу, коду ответа, браузеру, системе и дате, поиск по IP,
адресу страницы и логину. Статика (`/static/`, `/media/`, favicon) в журнал
не пишется, чтобы не засорять его.

**События покупателей** (`/admin/activity/authevent/`) — только значимые действия:

| Событие | Когда появляется |
|---|---|
| Регистрация | создан аккаунт |
| Неудачная регистрация | форма не прошла проверку (с текстом ошибки) |
| Вход / Неудачный вход | успешный и неуспешный вход, включая попытки с чужим паролем |
| Выход | покупатель вышел из аккаунта |
| Смена пароля | пароль изменён |
| Оформлен заказ | создан заказ — с номером, суммой и IP-адресом |

IP-адрес заказа виден и в обычном разделе заказов: колонка «IP-адрес» в списке,
поле в карточке заказа и поиск по IP.

**Как определяется IP.** Сайт на хостинге работает за прокси, поэтому адрес
берётся по цепочке: `X-Forwarded-For` (первый корректный адрес) → `X-Real-IP` →
`REMOTE_ADDR`. Некорректные значения отбрасываются, поддерживается и IPv6.
Если адрес определить не удалось, поле останется пустым — сайт при этом
продолжает работать: любая ошибка записи в журнал не мешает ответить посетителю.

**Отключить журнал.** Задайте переменную окружения `DJANGO_ACTIVITY_LOG=0`
(на Render — в разделе Environment, локально — перед запуском сервера).

**Почистить старые записи.** Журнал растёт, поэтому есть команда:

```
python manage.py clear_activity_log --days 30
python manage.py clear_activity_log --days 30 --dry-run
python manage.py clear_activity_log --days 7 --visits-only
```

`--dry-run` только показывает, сколько записей будет удалено.

**Сводка магазина на главной странице админки.** Откройте `/admin/` — над списком
разделов будет блок «Сводка магазина»:

| Карточка | Что показывает |
|---|---|
| Продажи | выручка, число заказов и средний чек за сегодня, 7 дней, 30 дней и за всё время (отменённые заказы не учитываются), ниже — счётчики по статусам |
| Топ товаров по продажам | первые пять товаров по проданным штукам с суммой выручки; длина полосы пропорциональна продажам |
| Склад и витрина | сколько товаров и категорий, у скольких нулевой остаток, что скрыто с витрины, и список товаров, которых осталось 5 штук и меньше |
| Активность | посещения за сегодня и 7 дней, уникальные IP, вошедшие покупатели, регистрации, заказы и неудачные входы — из журнала активности |
| Последние заказы | пять последних заказов с покупателем, IP, суммой, статусом и ссылкой на карточку |
| Новые обращения | последние сообщения из формы обратной связи |

Как это устроено:

- админ-панель использует свой класс `GameZoneAdminSite` (`gamezone/admin.py`),
  он подключён через `gamezone.admin.GameZoneAdminConfig` в `INSTALLED_APPS` —
  поэтому заголовок и оформление свои, а все модели регистрируются как обычно;
- данные собирает `shop/dashboard.py` функцией `build_dashboard(user)`:
  только агрегаты ORM (`Sum`, `Count`, `Avg`) по реальным записям, ничего
  не придумывается и не округляется «для красоты»;
- каждая карточка показывается только при наличии права на просмотр
  соответствующей модели: кладовщик с доступом к товарам не увидит выручку;
- если данных пока нет, карточка показывает пустое состояние, а не пропадает;
- стили (`shop/static/shop/css/admin-dashboard.css`) используют CSS-переменные
  темы админ-панели, поэтому карточки сводки автоматически совпадают
  с оформлением витрины, а графики сделаны на CSS без сторонних библиотек.

Порог «заканчивающихся» товаров задан константой `LOW_STOCK_THRESHOLD`
в `shop/dashboard.py` (по умолчанию 5 штук).

**Про приватность.** IP-адрес относится к персональным данным. Раздел сделан
для учебного проекта: не публикуйте журнал, не выгружайте его в открытый
доступ и не храните дольше, чем нужно.

## Отзывы и рейтинги

Отзывы лежат в модели `Review` (`shop/models.py`): товар, автор, оценка 1–5,
текст до 2000 символов, признак «показывать на сайте», дата.

Правила, которые проверяет сервер:

- отзыв может оставить только вошедший покупатель, у которого есть заказ
  с этим товаром (отменённые заказы не считаются);
- на пару «товар + покупатель» — один отзыв: повторная отправка формы
  обновляет свой отзыв, а не создаёт второй;
- пустой текст допустим, оценка обязательна;
- скрытый администратором отзыв не участвует ни в средней оценке, ни в списке.

Средняя оценка и количество отзывов считаются в базе одним запросом
(`shop.models.with_rating`), поэтому каталог не делает по два запроса на
каждую карточку. Звёзды нарисованы SVG-иконками и заливаются на ширину
рейтинга через CSS — без картинок и сторонних библиотек.

Демо-отзывов в `seed_data` нет: пока реальный покупатель не напишет отзыв,
в карточке показывается «Отзывов пока нет».

## Выгрузка в CSV и остатки в админке

В списках админки выберите записи, затем в меню «Действие» — «Выгрузить в CSV
(Excel)». Доступно для товаров, заказов (плюс отдельная выгрузка позиций),
отзывов, профилей, обращений и обоих журналов активности.

Файл выгружается с учётом фильтров и поиска: например, отфильтруйте товары по
категории и выгрузите только их. Формат рассчитан на Excel: разделитель «;»,
UTF-8 с BOM, даты в виде `21.10.2026 14:30`, суммы с двумя знаками после точки,
булевы значения — «да»/«нет». Имя файла содержит дату, например
`orders-2026-10-21.csv`.

Для остатков в списке товаров добавлены:

- колонка «Наличие» с метками «Достаточно», «Заканчивается» (остаток
  не больше 5 шт.), «Нет в наличии» и «Снят с продажи»;
- фильтр «остаток на складе» с этими же вариантами;
- предупреждение в форме товара, если остаток уже на пороге.

Порог задаётся одной константой `LOW_STOCK_THRESHOLD` в `shop/models.py`
и используется и в админке, и в сводке на главной странице.

## Промокоды

Промокод — модель `Coupon`: код, тип скидки (процент или фиксированная сумма),
минимальная сумма заказа, срок действия, лимит применений, счётчик применений.

Как это работает:

- код вводится в корзине, приводится к верхнему регистру и проверяется на сервере:
  существование, включённость, срок, лимит и минимальная сумма;
- код может быть набран в любом регистре и с пробелами — `GAMEZONE10`, `gamezone10`
  и ` gamezone10 ` это один и тот же промокод. Разрешены латинские и кириллические
  буквы, цифры, дефис и подчёркивание (от 2 до 32 символов), поэтому код вроде
  «ШКАФИФИ» тоже работает;
- скидка пересчитывается при каждом показе корзины (если промокод отключили,
  скидка исчезает сама);
- при оформлении заказа промокод фиксируется в `Order.coupon`,
  скидка — в `Order.discount_amount`, а `Order.total_amount` хранит итог
  к оплате; счётчик применений увеличивается в той же транзакции под
  `select_for_update()`, поэтому лимит нельзя превысить двумя заказами сразу;
- при отмене заказа применение возвращается (счётчик уменьшается);
- в админке есть раздел «Промокоды» с выгрузкой в CSV и массовым включением.
  Код проверяется до записи в базу: если такой промокод уже есть, форма покажет
  «Промокод «ШКАФИФИ» уже существует — выберите другой код», а не ошибку базы.
  Сравнение идёт без учёта регистра и пробелов, поэтому повтор «Шкафифи»
  к уже созданному «ШКАФИФИ» не пройдёт.

Демо-коды создаёт `seed_data`: `GAMEZONE10` (−10 % от 1000 ₴) и
`WELCOME200` (−200 ₴ от 2000 ₴). Свои коды добавляйте в админке: раздел
«Промокоды» → «Добавить».

## Избранное и «С этим покупают»

Избранное хранится в сессии (`request.session['favorites']`) — как и корзина,
поэтому работает без регистрации. Ограничение — 60 товаров: при переполнении
удаляется самый старый. Счётчик в шапке считает позиции на каждой странице.

Блок «С этим покупают» строится функцией `shop/recommendations.py:bought_together`:
берутся заказы, где уже есть этот товар (кроме отменённых), и товары из тех же
заказов сортируются по частоте совместных покупок. Если совместных покупок
ещё не было, блок не выводится — случайные товары не подставляются.

## Кабинет заказа и печатный чек

В кабинете у каждого заказа виден таймлайн статусов и две ссылки: «Открыть
заказ» и «Чек». Страница заказа (`/accounts/orders/<номер>/`) показывает:

- шаги «Заказ оформлен → Подтверждён → Отправлен → Завершён» с отметкой
  текущего шага (для отменённого — отдельный шаг «Отменён»);
- состав заказа, скидку и итог;
- адрес доставки и контактные данные;
- кнопку «Отменить заказ», пока статус «Новый» или «Подтверждён».

Отмена выполняется в транзакции: остатки товаров возвращаются на склад,
статус меняется на «Отменён», промокод освобождается. После «Отправлен»
отмена недоступна — кнопка заменяется пояснением.

Чек (`/order/<номер>/receipt/`) — самостоятельная страница без шапки сайта,
с правилами `@media print`: кнопка «Печать» открывает системный диалог, а при
печати убираются кнопки и остаётся белый лист с таблицей позиций. Доступ к чеку
есть у владельца заказа, у персонала и у сессии, в которой заказ только что
оформлен, — чужой номер ничего не откроет.

## Управление статусами заказов

Правила переходов описаны в одном месте — `Order.STATUS_FLOW` в `shop/models.py`:

```
Новый       → Подтверждён, Отменён
Подтверждён → Отправлен, Отменён
Отправлен   → Завершён
Завершён    → (конечный статус)
Отменён     → (конечный статус)
```

Изменения выполняет `shop/orders.py`: `change_status()` проверяет переход
и пишет его в базу, `cancel_order()` дополнительно возвращает остатки товаров
на склад и уменьшает счётчик применений промокода — всё в одной транзакции
с `select_for_update()`. Тот же код использует кнопка «Отменить заказ»
в личном кабинете покупателя, поэтому правила не расходятся между витриной
и админкой.

В админке доступны два способа:

- **кнопки в карточке заказа** — над формой, только для разрешённых переходов;
  каждая кнопка отправляет POST с CSRF-токеном на отдельный адрес
  `/admin/shop/order/<id>/transition/<статус>/`;
- **массовые действия в списке** — «Подтвердить / Отправить / Завершить /
  Отменить выбранные заказы». Заказы, для которых переход невозможен,
  пропускаются, а в сообщении видно, сколько изменено и сколько пропущено.

Кнопки и действия видны только сотрудникам с правом изменения заказа;
при праве только на просмотр их нет.

В шапке админки показывается счётчик заказов в статусе «Новый» со ссылкой
на список с готовым фильтром. Если новых заказов нет или у сотрудника нет
доступа к заказам, счётчик не выводится.

## Почта и восстановление пароля

Восстановление использует стандартные представления Django и свои шаблоны
в `templates/registration/` (папка уровня проекта, потому что такие же шаблоны
есть в `django.contrib.admin` и перекрыли бы наши).

По умолчанию письма выводятся **в консоль сервера** — учебный проект не
отправляет реальную почту. Чтобы письма действительно уходили, задайте
переменные окружения:

| Переменная | Значение |
|---|---|
| `DJANGO_MAIL_BACKEND` | `django.core.mail.backends.smtp.EmailBackend` |
| `DJANGO_EMAIL_HOST` | SMTP-сервер, например `smtp.gmail.com` |
| `DJANGO_EMAIL_PORT` | порт, по умолчанию `587` |
| `DJANGO_EMAIL_USER` | логин SMTP |
| `DJANGO_EMAIL_PASSWORD` | пароль или пароль приложения |
| `DJANGO_EMAIL_TLS` | `1` (TLS включён) или `0` |
| `DJANGO_DEFAULT_FROM_EMAIL` | адрес отправителя |

Настройки собраны в `MAILERS` (новый формат Django 6.1; старые `EMAIL_*`
объявлены устаревшими до Django 2028). Ссылка в письме живёт 24 часа, после
смены пароля становится недействительной. Для чужого адреса сайт отвечает так
же, как для существующего, — чтобы нельзя было выяснить, есть ли такой аккаунт.

## Оформление админ-панели

Админка выглядит как витрина: та же тёмная палитра, шрифт Inter, логотип
и фиолетово-бирюзовые акценты. Посторонние библиотеки тем не используются —
только один свой CSS-файл и два шаблона.

Что где лежит:

| Файл | Назначение |
| --- | --- |
| `templates/admin/base_site.html` | шапка с логотипом и названием, ссылка «Открыть магазин», подключение темы, favicon и шрифт |
| `templates/admin/index_with_dashboard.html` | главная страница `/admin/` со сводкой |
| `shop/static/shop/css/admin-theme.css` | вся тема: переменные цветов и оформление списков, форм, фильтров, кнопок, страницы входа |
| `shop/static/shop/css/admin-dashboard.css` | карточки и графики сводки |

Как это работает:

- Django рисует админку по своим шаблонам из `django/contrib/admin`, а
  проект подменяет только `base_site.html` — от него наследуются все страницы,
  поэтому тема появляется сразу везде: главная, списки, карточки записей,
  фильтры, страница входа;
- папка шаблонов уровня проекта подключена в `gamezone/settings.py` через
  `TEMPLATES → DIRS`, потому что приложение `django.contrib.admin` стоит в
  `INSTALLED_APPS` раньше `shop` и шаблоны приложения его не перекрывают;
- в `admin-theme.css` переопределены CSS-переменные Django (`--primary`,
  `--body-bg`, `--link-fg`, `--hairline-color` и остальные) сразу для всех
  значений атрибута `data-theme` (`light`, `dark`, `auto`), поэтому тема одна
  и та же при любом системном оформлении, а переключатель темы скрыт;
- сводка использует те же переменные, поэтому карточки и графики подхватывают
  новое оформление без правок в своём файле.

Если нужно вернуть стандартный вид Django — удалите подключение
`shop/css/admin-theme.css` из `templates/admin/base_site.html`, всё остальное
продолжит работать.

## Почему после перезапуска пропадают пользователи

Данные сайта (пользователи, заказы, профили, обращения, журналы) лежат в базе.
По умолчанию это файл **`db.sqlite3` рядом с `manage.py`**. Дальше всё зависит
от того, где запущен сайт.

### Локально на компьютере

Файл `db.sqlite3` никуда не девается при перезапуске сервера: `run.bat` только
применяет миграции и добавляет демо-товары, если каталог пуст. Он ничего
не удаляет. Если пользователи всё же пропали, причина обычно одна из двух:

- проект распакован заново из архива в новую папку — файла `db.sqlite3` в архиве
  нет (он в `.gitignore`), поэтому база создаётся пустой;
- папка проекта скопирована или перемещена без файла `db.sqlite3`.

Лечится просто: держите одну папку проекта и периодически делайте копию данных
(`backup.bat`), а файл `db.sqlite3` копируйте вместе с папкой.

### На бесплатном хостинге (Render и подобные)

Здесь причина другая и она не исправляется настройками проекта: **файловая
система бесплатного контейнера эфемерная**. При каждом перезапуске, деплое или
пробуждении после сна контейнер создаётся заново, и файл `db.sqlite3`
появляется пустым. Демо-товары возвращаются сами (их создаёт `seed_data`),
а вот зарегистрированные покупатели, заказы и журналы — нет.

Единственное правильное решение — вынести базу за пределы контейнера,
в внешний **PostgreSQL**. Проект к этому уже готов: `dj-database-url`
и `psycopg2-binary` есть в `requirements-prod.txt`, а настройки читают
переменную `DJANGO_DATABASE_URL`. **Код менять не нужно.**

Пошагово на примере бесплатного Neon:

1. Зарегистрируйтесь на [neon.tech](https://neon.tech) и создайте проект —
   база выдаётся бесплатно и данные в ней не стираются при перезапуске сайта.
2. Скопируйте строку подключения (Connection string). Она выглядит так:
   `postgres://пользователь:пароль@ep-что-то-там.neon.tech/имябазы?sslmode=require`
3. В Render откройте ваш сервис → **Environment** → добавьте переменную
   `DJANGO_DATABASE_URL` и вставьте эту строку значением.
4. Сохраните и запустите деплой (**Manual Deploy** → **Deploy latest commit**).
5. При старте команда запуска сама применит миграции к новой базе, добавит
   демо-товары и создаст администратора из переменных
   `DJANGO_SUPERUSER_USERNAME` / `DJANGO_SUPERUSER_PASSWORD`.
6. Проверить, какая база подключена, можно командой
   `python manage.py db_status` (локально) или по первым строкам лога деплоя:
   команда запускается при старте контейнера и пишет либо «База: SQLite …
   данные не переживут перезапуск», либо «База: postgresql, хост … — данные
   сохраняются между перезапусками». Флаг `--ping` дополнительно проверяет,
   что к базе действительно можно подключиться.

Проверено: строка подключения с `?sslmode=require` превращается в настройки
PostgreSQL с включённым SSL (`ENGINE: django.db.backends.postgresql`,
`OPTIONS: {'sslmode': 'require'}`, `CONN_MAX_AGE: 600`) — именно то, что
требуют облачные базы.

Альтернативы: Supabase, ElephantSQL, Railway, любая PostgreSQL на VPS.
Важно про базу от самого Render: бесплатный PostgreSQL у Render живёт
**30 дней**, потом удаляется, поэтому для учебного проекта удобнее внешний
сервис без такого срока. Постоянный диск (Persistent Disk), на котором
SQLite пережил бы перезапуск, доступен только на платном тарифе Render.

### Перенос данных в новую базу

Если в старой базе уже есть покупатели и заказы, перенесите их так:

```
python manage.py backup_data
```

затем задайте `DJANGO_DATABASE_URL`, примените миграции к новой базе
(`python manage.py migrate`) и верните данные:

```
python manage.py restore_data backups/gamezone-2026-10-20-153000.json
```

Тот же порядок работает при переезде с компьютера на хостинг и обратно.

### Команды и батники резервных копий

| Чем | Что делает |
|---|---|
| `backup.bat` | Копия в `backups\gamezone-<дата и время>.json` (двойной клик) |
| `backup.bat --with-logs` | То же плюс журнал посещений и событий |
| `restore.bat` | Показывает содержимое самой свежей копии, спрашивает подтверждение и восстанавливает |
| `restore.bat путь\к\файлу.json` | Восстановить конкретный файл (можно перетащить файл на батник) |
| `python manage.py backup_data --output копия.json` | То же из командной строки, в указанный файл |
| `python manage.py restore_data копия.json --show` | Только посмотреть, что внутри копии |

Что попадает в копию: пользователи (с хэшами паролей — вход после
восстановления работает теми же паролями), группы, профили, заказы и их
позиции, товары, категории, обращения. Журналы активности — только с флагом
`--with-logs`. Связи сохраняются по естественным ключам, поэтому заказ
после восстановления остаётся привязан к своему покупателю.

Чего в копии нет: загруженные через админку изображения (папка `media/`) —
их копируйте отдельно, и сама база `db.sqlite3` (копия — это данные, а не файл
базы).

Про хранение: папка `backups/` добавлена в `.gitignore` — в репозиторий копии
не попадают. Не публикуйте файл копии: внутри email и телефоны покупателей.
И помните, что на Render файл копии так же исчезнет при перезапуске, как и
сама база, — копии делайте локально, а на хостинге используйте PostgreSQL.

## Решение частых проблем

**Ошибка `no such table: auth_user` (или других таблиц) при входе в `/admin/`**

Значит, к базе данных не применялись миграции (сервер может запускаться,
но таблицы ещё не созданы). Выполните в папке, где лежит `manage.py`:

```
python manage.py migrate
python manage.py seed_data
```

Затем перезапустите сервер и создайте администратора (`create_admin.bat`
или `python manage.py createsuperuser`). Батник `create_admin.bat` теперь
и сам применяет миграции перед созданием администратора.

**Проект открыт в PyCharm**

Выполняйте команды в терминале PyCharm — той же виртуальной средой,
которой запускается сервер. Зависимости ставьте из `requirements.txt`:

```
pip install -r requirements.txt
```

Проект разработан и проверен на Django 6.1 (последняя ветка) и Python 3.12+.
Зависимости ставьте только из `requirements.txt` — там указана проверенная
ветка Django (`>=6.1,<7.0`). Держать одновременно сервер из PyCharm и `run.bat`
не нужно: оба занимают порт 8000. Если порт уже занят, `run.bat` это заметит
и предложит открыть работающий магазин в браузере либо запуститься на другом
порту (`run.bat 8080`).

**На хостинге сайт отвечает ошибкой 400 на все страницы**

Значит, `DJANGO_DEBUG=0`, но не задан `DJANGO_ALLOWED_HOSTS` — Django не знает,
какие домены считать своими. Теперь в этом случае проект не стартует и пишет
в лог понятное сообщение с примером. Задайте переменную на хостинге:

```
DJANGO_ALLOWED_HOSTS=ваш-сервис.onrender.com
```

**При деплое ошибка `UnknownSchemeError: Scheme '://' is unknown`**

Так бывает, когда в переменную `DJANGO_DATABASE_URL` попала не строка
подключения целиком, а её часть: потерялось начало `postgresql://`, значение
скопировано вместе с разметкой (квадратные скобки, `mailto:`, кавычки),
с переносом строки или с HTML-экранированием `&amp;` вместо `&`.

Проект такие значения сам приводит в порядок: убирает пробелы, переносы строк,
кавычки и невидимые символы, заменяет `&amp;` на `&`, отбрасывает случайно
скопированное имя переменной и возвращает потерянную схему. Если привести
значение не удаётся, запуск останавливается с понятным сообщением на русском,
в котором нет вашего пароля.

Проверьте значение в Render → Environment: оно должно быть одной строкой вида

```
postgresql://neondb_owner:ПАРОЛЬ@ep-что-то.neon.tech/neondb?sslmode=require
```

без пробелов в начале и конце, без кавычек, без угловых и квадратных скобок,
без `DJANGO_DATABASE_URL=` внутри значения и с обычным `&` между параметрами.
Проще всего скопировать его в Neon заново: **Connection Details** →
**Connection string** (для бесплатного тарифа подходит и pooled-вариант
с `-pooler` в адресе).

**Сборка на хостинге ищет Dockerfile и не находит его**

Так выглядит сервис, созданный с рантаймом Docker. Либо перезапустите деплой
(`Dockerfile` в проекте есть), либо создайте сервис заново с рантаймом
**Python 3** — тогда используются команды из `render.yaml`.

**Ошибка про `WindowsApps\python.exe` при запуске батников**

Это подставла Microsoft Store, а не настоящий Python. Установите Python
с [python.org](https://www.python.org/downloads/) — батники автоматически
используют лаунчер `py` (установщик ставит его вместе с Python).

**Пароль при создании администратора «не вводится»**

Стандартный запрос `createsuperuser` скрывает символы и в некоторых
консолях Windows не принимает ввод. Используйте `create_admin.bat` —
логин и пароль набираются обычным видимым текстом.

## Изображения товаров

У товара есть необязательное поле `image` (ImageField). Демонстрационные товары
используют локальные SVG-иллюстрации из `shop/static/shop/images/` — поэтому

## Как вывести сайт в интернет

### Почему не Netlify

Netlify раздаёт статические файлы и serverless-функции на JavaScript, TypeScript
и Go. Python там доступен только на этапе сборки, поэтому запустить Django-сервер
на Netlify нельзя — это ограничение платформы, а не проекта. Магазину нужен
постоянно работающий процесс: база данных, сессии корзины, оформление заказов,
админ-панель.

На Netlify можно выложить только **статическую копию** страниц (витрину):
главная, каталог и карточки товаров будут видны, но корзина, оформление заказа,
поиск, фильтры и админка работать не будут — им нужен сервер.

Дальше — два бесплатных способа опубликовать именно **работающий** магазин.

### Вариант 1. Render — деплой из GitHub, бесплатно

Всё нужное уже лежит в проекте: `render.yaml`, `Procfile`, `.python-version`,
`requirements-prod.txt`, команда `ensure_admin` и боевые настройки
в `gamezone/settings.py`.

1. Проект должен лежать в репозитории GitHub. При создании сервиса выберите
   ветку, в которой находится код.
2. Откройте <https://render.com>, войдите через GitHub.
3. **New +** → **Blueprint** → выберите репозиторий. Render найдёт `render.yaml`
   и сам создаст сервис с нужными командами.
   (Можно и **New +** → **Web Service** — тогда команды возьмите из `render.yaml`:
   build — `pip install -r requirements-prod.txt && python manage.py collectstatic --noinput`,
   start — `python manage.py migrate --noinput && python manage.py seed_data --if-empty
   && python manage.py ensure_admin && gunicorn gamezone.wsgi:application`.)
4. В разделе **Environment** задайте три переменные:

   | Переменная | Что указать |
   |---|---|
   | `DJANGO_ALLOWED_HOSTS` | адрес сервиса, например `gamezone.onrender.com` |
   | `DJANGO_SUPERUSER_USERNAME` | логин администратора (придумайте свой) |
   | `DJANGO_SUPERUSER_PASSWORD` | пароль администратора (придумайте свой) |
   | `DJANGO_DATABASE_URL` | строка подключения внешней базы PostgreSQL — **обязательно**, если хотите, чтобы пользователи и заказы не пропадали после перезапуска (подробнее ниже) |

   `DJANGO_DEBUG=0` и `DJANGO_SECRET_KEY` уже прописаны в `render.yaml`
   (ключ Render сгенерирует сам — в коде проекта паролей и ключей нет).
   Необязательная переменная `DJANGO_ACTIVITY_LOG=0` отключает журнал
   посещений — по умолчанию он включён.
5. Дождитесь конца сборки. Render сам поставит зависимости, соберёт статику,
   применит миграции, добавит демо-товары, создаст администратора
   и запустит gunicorn.
6. Откройте `https://ваш-сервис.onrender.com/` и
   `https://ваш-сервис.onrender.com/admin/`.

**Если Render собирает проект как Docker.** При создании сервиса вручную можно
случайно выбрать рантайм Docker вместо Python — тогда в логе сборки будет
`failed to read dockerfile: open Dockerfile: no such file or directory`.
В проекте есть `Dockerfile`, поэтому достаточно перезапустить деплой
(**Manual Deploy** → **Deploy latest commit**). При желании рантайм можно
сменить на Python 3: **Settings** → **Build** → **Source** → **Edit** →
выбрать Python 3 и указать команды из `render.yaml`.

Честно об ограничениях бесплатного тарифа Render:

- сервис засыпает примерно после 15 минут без посетителей и просыпается
  около минуты — первый заход будет медленным;
- файловая система временная: при каждом новом деплое база создаётся заново.
  Миграции, демо-товары и администратор восстанавливаются автоматически
  (это делает start-команда), а вот товары, добавленные вами через админку,
  и оформленные заказы пропадут;
- чтобы данные жили постоянно, подключите бесплатный PostgreSQL
  (например, Neon или Supabase) и задайте переменную `DJANGO_DATABASE_URL`
  со строкой подключения — проект её понимает;
- загруженные через админку картинки хранятся на диске сервиса и тоже
  сбрасываются при деплое;
- трафик — 5 ГБ в месяц.

### Вариант 2. PythonAnywhere — бесплатно, база не пропадает

Здесь SQLite лежит на настоящем диске, поэтому добавленные товары и заказы
сохраняются. Сайт будет по адресу `ваш-логин.pythonanywhere.com`.

1. Зарегистрируйтесь на <https://www.pythonanywhere.com> (тариф Beginner — $0).
2. Загрузите файлы проекта: через вкладку **Files** или в консоли
   **Bash** командой `git clone`.
3. В консоли Bash, в папке проекта:

   ```bash
   python3 -m venv .venv
   .venv/bin/pip install -r requirements.txt
   .venv/bin/python manage.py migrate
   .venv/bin/python manage.py seed_data
   .venv/bin/python manage.py collectstatic --noinput
   .venv/bin/python manage.py createsuperuser
   ```

4. **Web** → **Add a new web app** → **Manual configuration** → версия Python
   3.12 или новее.
5. В настройках приложения укажите **Virtualenv** — путь к папке `.venv`.
6. Откройте **WSGI configuration file** и приведите его к такому виду
   (путь — к вашей папке проекта):

   ```python
   import os
   import sys

   path = '/home/ваш-логин/GameZone'
   if path not in sys.path:
       sys.path.append(path)

   os.environ['DJANGO_SETTINGS_MODULE'] = 'gamezone.settings'
   os.environ['DJANGO_DEBUG'] = '0'
   os.environ['DJANGO_SECRET_KEY'] = 'ваш-длинный-случайный-ключ'
   os.environ['DJANGO_ALLOWED_HOSTS'] = 'ваш-логин.pythonanywhere.com'

   from django.core.wsgi import get_wsgi_application
   application = get_wsgi_application()
   ```

   Этот файл живёт на сервере и не попадает в репозиторий, поэтому ключ
   в нём допустим. Никому не показывайте его и не публикуйте.
7. В разделе **Static files** добавьте соответствие: URL `/static/` →
   директория `/home/ваш-логин/GameZone/staticfiles/`.
8. Нажмите **Reload** и откройте сайт.

Ограничения бесплатного тарифа: один сайт, 512 МБ диска, адрес только
на `pythonanywhere.com` (свой домен — платно), исходящий доступ в интернет
только к разрешённым адресам, и примерно раз в месяц нужно заходить
и нажимать «продлить» (Extend), иначе сайт останавливают.

### Настройки, которые обязательно задать при публикации

1. `DJANGO_DEBUG=0` — без этого в интернет уйдут технические страницы ошибок
   с кодом и настройками.
2. `DJANGO_SECRET_KEY` — свой длинный случайный ключ, не тот, что в коде.
3. `DJANGO_ALLOWED_HOSTS` — домен вашего сайта (через запятую, если их несколько).
   Домены из этой переменной автоматически попадают в `CSRF_TRUSTED_ORIGINS`,
   поэтому формы корзины и оформления заказа работают по HTTPS без 403.
4. Статика: `python manage.py collectstatic --noinput` и её раздача
   (WhiteNoise на Render, сопоставление `/static/` на PythonAnywhere).
5. Пароль администратора — только в переменных окружения
   (`DJANGO_SUPERUSER_USERNAME`, `DJANGO_SUPERUSER_PASSWORD`), никогда в коде.
6. `db.sqlite3`, `.venv` и ключи не коммитятся — это уже настроено в `.gitignore`.
7. Почта (по желанию): `DJANGO_MAIL_BACKEND`, `DJANGO_EMAIL_HOST`,
   `DJANGO_EMAIL_PORT`, `DJANGO_EMAIL_USER`, `DJANGO_EMAIL_PASSWORD`,
   `DJANGO_EMAIL_TLS`, `DJANGO_DEFAULT_FROM_EMAIL` — без них письма
   восстановления пароля печатаются в консоль сервера. Пароль приложения
   SMTP храните только в переменных окружения.

При `DEBUG=False` проект дополнительно включает HTTPS-редирект, защищённые
cookies сессий и CSRF, а также HSTS на один час — это стандартный набор
для учебного сайта за HTTPS-прокси.

### Проверить боевой режим локально

Перед публикацией полезно убедиться, что всё работает при `DEBUG=0`.
В PowerShell, в папке проекта:

```
pip install -r requirements-prod.txt
$env:DJANGO_DEBUG="0"
$env:DJANGO_SECRET_KEY="длинный-случайный-ключ-для-проверки"
$env:DJANGO_ALLOWED_HOSTS="127.0.0.1,localhost"
$env:DJANGO_SSL_REDIRECT="0"
python manage.py collectstatic --noinput
python manage.py migrate
python manage.py runserver
```

`DJANGO_SSL_REDIRECT="0"` нужен только для локальной проверки: на хостинге сайт
работает по HTTPS и редирект там включён, а локально он отправил бы браузер
на несуществующий `https://127.0.0.1:8000`.

Сайт откроется на <http://127.0.0.1:8000/> в том же режиме, в каком будет
работать на хостинге. Вернуть обычную разработку: закройте окно и запустите
`run.bat` (переменные окружения живут только в этом окне PowerShell).

## Честные оговорки

- Цены и товары — демонстрационные, это не актуальные рыночные предложения.
- Оплата не подключена: заказ только сохраняется в SQLite.
- Письма не отправляются по умолчанию: без настроек SMTP письмо для смены
  пароля печатается в консоль сервера, а обращения с формы связи только
  сохраняются в базе.
- Блок «С этим покупают» использует реальные заказы, а отметка «Топ»
  и сортировка «По популярности» остаются демонстрационными.
- Статус «По популярности» в каталоге — демонстрационный критерий
  (рекомендуемые товары выводятся первыми).
- Отзывы, избранное и промокоды работают по-настоящему, но демо-отзывов
  и «купленных» оценок нет: отзыв пишет только покупатель товара.
